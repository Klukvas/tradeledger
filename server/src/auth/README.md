# Authentication

Outside production, public registration creates User, Workspace, empty Dataset and Session in one database transaction. In production the HTTP controller always rejects public registration with 403 before hashing or database work. Trusted local provisioning may call AuthService.register directly; there is no HTTP allowlist or temporary registration window. The server uses no local fallback and has no seeded credentials. Email is trimmed and lowercased; passwords preserve whitespace and require 12–256 UTF-16 code units.

Passwords use asynchronous Node scrypt with a random 16-byte salt, 64-byte derived key, versioned encoding and the fixed profile N=131072, r=8, p=1. This matches [OWASP's scrypt recommendation](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Verification accepts only that profile; malformed parameters cannot increase resource usage. Two jobs may run concurrently, with at most eight waiting; additional work gets 429. Startup derives a dummy hash from random data for unknown-email verification. No default password is created.

Opaque session tokens contain 32 random bytes. Only SHA-256 token hashes persist; cookies use HttpOnly, SameSite=Lax and path=/, and Secure whenever required by AppConfig. Logout revokes the request token via UPDATE and never emits Set-Cookie. This prevents a delayed logout response from erasing a newer cookie issued by another tab's login. A retained revoked cookie cannot authenticate; a subsequent login replaces it. Guards resolve user/workspace identity from the database on every protected request.

Auth throttling uses the socket IP by default (`TRUST_PROXY_HOPS=0`). The production topology uses exactly one Caddy ingress and `TRUST_PROXY_HOPS=1`; Caddy replaces incoming forwarded client headers and the API has no public host port. Express trusts only the nearest hop, never an unbounded forwarding chain. See [the proxy contract](../../../API_CONTRACTS.md#configuration-and-composition). Production defaults per minute: 10 registrations and 30 logins per IP, 300 accepted auth attempts across the process. Loopback development permits 100 registrations and 100 logins per IP, 2000 total. Buckets and the scrypt queue are bounded. These limits are process-local and require shared coordination before scaling to multiple API instances; reverse proxies must preserve an appropriate deployment-wide limit. Tests can override the `AUTH_LIMITS` DI provider with `AuthLimits` from this module; no HTTP bypass or reset endpoint exists.
