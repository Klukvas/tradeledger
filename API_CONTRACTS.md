# Server contracts

This document describes the current HTTP API, authentication, PostgreSQL persistence and server coordination. It complements the [domain contract](./CONTRACTS.md); the [architecture map](./ARCHITECTURE.md) links the implementation. [src/domain/types.ts](./src/domain/types.ts) is the source of domain types; [shared/api.ts](./shared/api.ts) defines transport types and contains no server runtime imports. The server imports the pure domain engine directly.

## HTTP

All routes have the `/api` prefix. JSON responses use `ApiResult<T>`: `{ok:true,value:T}` or `{ok:false,error:{code,message}}`. Domain error codes remain valid; transport adds UNAUTHENTICATED (401), FORBIDDEN (403), RATE_LIMITED (429), UNAVAILABLE (503). VALIDATION is 400 (including malformed JSON), NOT_FOUND 404, CONFLICT 409; oversized JSON is 413 with VALIDATION. Unknown exceptions return a generic 500 STORAGE error without SQL, stack, environment values, request bodies or credentials. No CORS is enabled.

Runtime outages return the sanitized 503 UNAVAILABLE envelope: Prisma initialization errors; connection/timeout/pool codes P1001/P1002/P1008/P1017/P2024/P2037; driver ECONNREFUSED/ETIMEDOUT/ECONNRESET/ENOTFOUND; and structured Prisma DriverAdapterError causes DatabaseNotReachable/ConnectionClosed/SocketTimeout/TooManyConnections/TlsConnectionError, including meta.driverAdapterError wrappers. Explicit DatabasePoolTimeoutError tags are supported; untagged generic errors are never classified by their message. Constraint failures are not classified as outages.

Every unsafe request (including register, login and logout) requires an exact configured `Origin` and `X-TradeLedger-Request: 1`. Missing, null and foreign origins are rejected with 403. Vite proxies `/api` to `http://127.0.0.1:5180` preserving Origin. The JSON envelope limit is 6 MiB. Imports additionally limit the canonical validated source DocumentV1 to 5 MiB measured in UTF-8 bytes. Exceeding either size limit returns 413 VALIDATION; malformed JSON and invalid document fields return 400. Auth additionally validates small bounded strings.

| Method | Route | Request | Success value |
|---|---|---|---|
| POST | `/auth/register` | AuthRequest | Development/test: AuthResponse and new session cookie; production: 403 FORBIDDEN |
| POST | `/auth/login` | AuthRequest | AuthResponse, new session cookie |
| GET | `/auth/me` | — | AuthResponse, or 401 |
| POST | `/auth/logout` | `{}` | null; revoke session without Set-Cookie |
| GET | `/ledger` | — | DocumentV1 |
| POST | `/ledger/commands` | CommandRequest | CommandResponse |
| GET | `/ledger/export` | — | DocumentV1 from authoritative server read |
| POST | `/ledger/import` | ImportRequest | ImportResponse |
| GET | `/ledger/imports/:requestId` | — | persisted ImportReceipt, or 404 |
| GET | `/ledger/datasets` | — | DatasetListResponse; archived datasets only |
| GET | `/ledger/datasets/:id/export` | — | owner-scoped DocumentV1, or 404 |
| GET | `/health/ready` | — | ReadyResponse; 503 if real DB unavailable |

All ledger routes and POST `/auth/logout` require `X-TradeLedger-User` containing the public user ID captured by the initiating frontend operation. `SessionGuard` authenticates the cookie first, then requires that header to match the authenticated user exactly; missing or mismatched context returns 401 UNAUTHENTICATED before any handler or mutation, without revoking a session or clearing a cookie. The header only constrains the cookie identity and never selects an owner. GET `/auth/me` is explicitly exempt from the context check so it can establish the current identity; login remains public. Public registration is available only outside production. With `NODE_ENV=production`, `/auth/register` always returns 403 FORBIDDEN before credential validation, password hashing, account/workspace creation or session issuance. The production gate belongs to the HTTP controller; trusted local provisioning can still call `AuthService.register` without opening an HTTP registration window. There is no email allowlist, registration-enable environment override or administrator backdoor. This binding applies to reads, exports, receipt reads, archived datasets, commands and imports, protecting against cross-tab cookie changes even when BroadcastChannel notifications are delayed or unavailable and revisions coincide. All ledger routes require a session and scope every database access to its cookie-authenticated owner. Public user is `{id,email}`; password hashes, session tokens and workspace identifiers are never included. `AuthenticatedUser` is server-internal `{id,email,workspaceId}`. `server/src/auth` exports `SessionGuard`, `CurrentUser` and this type; `AuthModule` exports the guard. Registration creates the user, workspace and empty active dataset atomically. There is no default administrator or default credential. Passwords use scrypt. Sessions use opaque random tokens, with only their SHA hash in the database. Logout revokes the request's authenticated token and never emits Set-Cookie, including on success: a delayed A logout response cannot erase a cookie issued by a concurrent B login. A retained revoked cookie is rejected on subsequent authentication; the next login replaces it.

## Configuration and composition

`server/src/config` exports `APP_CONFIG`, `AppConfig`, `loadConfig` and global `ConfigModule`. Config fields: `databaseUrl`, `publicOrigin`, `port`, `host`, `isProduction`, `sessionCookieName`, `sessionTtlMs`, `secureCookies`, `trustProxyHops`. `DATABASE_URL` is required and never logged. `PUBLIC_ORIGIN` defaults to `http://127.0.0.1:5178`, port defaults to 5180 (`PORT`), bind host defaults to `127.0.0.1` (`HOST`; Docker sets `0.0.0.0`). Cookie name is `tradeledger_session`; lifetime is seven days. Production requires HTTPS and secure cookies. Insecure cookies are permitted only for explicit loopback HTTP development origins. Cookies are HttpOnly, SameSite=Lax, path=/, and secure according to config.

`TRUST_PROXY_HOPS` accepts only `0` or `1` and defaults to `0`, preserving direct loopback development. HTTP configuration applies the corresponding numeric Express `trust proxy` setting, so auth limits use the socket IP by default or the nearest forwarded client IP behind one proxy. Production sets `1` only with Caddy as the sole public ingress; API and PostgreSQL have no published host ports. Caddy overwrites forwarded client headers from its socket peer and does not trust incoming `X-Forwarded-For`; it forwards `/api/*` unchanged to the API. An extra leftmost forwarded address is ignored by the one-hop setting, but the setting alone cannot authenticate a direct caller: direct API exposure, a second proxy or Caddy `trusted_proxies` changes require a new proxy/rate-limit review. Never use unbounded `trust proxy=true`.

`AppModule` imports ConfigModule, DatabaseModule, AuthModule, LedgerModule, HealthModule and MonthlyCloseModule. Global HTTP setup installs cookie parsing, strict unsafe-request checking, bounded JSON parsing and the exception filter. `server/src/http` exports `configureHttp(app,config)` and `ApiException`/`ApiExceptionFilter`. Success envelopes are constructed by controllers (no implicit interceptor).

One npm workspace uses the root lockfile and `server/package.json` with CommonJS. Frontend root stays ESM. Backend compiles server/src, shared and directly imported src/domain into `server/dist`; entry is `server/dist/server/src/main.js`. Prisma 7 generator is `prisma-client`, output `server/src/generated/prisma`, `moduleFormat = "cjs"`; generated imports are extensionless (`importFileExtension = ""`). All Prisma packages are pinned to the same release. No prisma init or secret file generation.

## Persistence and module boundaries

`server/src/database` exports `DatabaseModule`, `DatabaseService` (PrismaClient), `LedgerRepository`, `Tx = Prisma.TransactionClient`, and `LockedWorkspace = {id,userId,activeDatasetId:string,revision:bigint,updatedAt:Date}`.

Repository methods:

- `read(userId:string):Promise<DocumentV1>` reads a RepeatableRead transaction.
- `withLockedWorkspace<T>(userId:string,run:(tx:Tx,workspace:LockedWorkspace)=>Promise<T>):Promise<T>` locks the workspace with owner predicate and parameterized FOR UPDATE.
- `readDocument(tx:Tx,workspace:LockedWorkspace):Promise<DocumentV1>`.
- `persistCommand(tx:Tx,workspace:LockedWorkspace,before:DocumentV1,after:DocumentV1,command:Command):Promise<void>` persists the changed normalized rows, histories and audit inside the caller transaction (using the explicit owner-locked workspace and its active dataset; no hidden transaction context or independent commit).
- `insertDataset(tx:Tx,workspaceId:string,document:DocumentV1,source:{kind:'backup'|'legacy',sourceHash:string},effectiveAt:Date):Promise<string>` inserts a fresh normalized dataset; caller performs activation and revision update atomically.
- `createWorkspace(tx:Tx,userId:string):Promise<string>` atomically bootstraps an empty dataset and workspace for registration.

Tables: User, Session, Workspace, Dataset, InventoryItem, InventoryMovement, Account, BalanceChange, Debt, Repayment, Snapshot, SnapshotAccount, AuditEvent, CommandReceipt, AccountHistory. Entity primary keys are composite `(datasetId,id)`; positions preserve every domain array order. DomainDocumentV1 is a JSON wire representation, not an authoritative JSON database blob. SQL safe-integer CHECKs protect monetary values, quantities and revisions. Composite `(workspaceId,activeDatasetId)` FK ensures active-dataset ownership. User rows own one workspace. History recorded for imported opening balances must identify its imported origin; historical operations are not fabricated. Server clock supplies timestamps for new operations; historical import dates remain intact.

Dataset additionally persists `sourceRevision`/`sourceUpdatedAt` from the imported document, separately from `archivedRevision`/`archivedDocumentUpdatedAt` (nullable while active). On archive, ImportService saves the former active workspace revision and updatedAt in those archive fields. An archived export uses those saved document metadata, so later active workspace revisions cannot change its exported document. After validating dataset ownership, ArchiveService constructs an explicit LockedWorkspace with archived dataset ID and its saved metadata for readDocument. No source revision is substituted for the workspace-global committed revision.

CommandReceipt primary key is `(workspaceId,requestId)`, with requestKind, requestHash, datasetId, committedRevision, committedAt, nullable sourceHash/counts. Request kind values are `command`, `backup`, `legacy`. Canonical SHA-256 hashes use shared/canonical.ts: command hash is the validated command with meta.at omitted (meta.commandId retained); expectedRevision is excluded. Import hash is canonical `{source,document}`; sourceHash is SHA-256 of the canonical source DocumentV1. Same request ID/hash returns the CURRENT document and `replayed:true` before revision CAS; changed payload or kind gives 409. An imported audit ID without an owned matching receipt is a conflict, never a silent replay.

`MutationModule` exports `MutationService.execute(userId:string,request:CommandRequest):Promise<CommandResponse>` and owns command coordination. `LedgerModule` imports AuthModule, MutationModule and DatabaseModule; its separate ImportService owns import coordination. Restore/import inserts a fresh dataset, archives the old dataset, activates the new dataset and records its receipt in one locked transaction. Workspace-global revision never resets on import. CAS checks the original version first. If missed monthly closes were inserted into the old dataset, its archive metadata uses revision + 1 / operation time and the imported active dataset uses revision + 2; otherwise import increments once. Both transitions commit atomically and require sufficient safe-integer revision headroom. Failure preserves active data and prior datasets. Receipt counts are inventory/accounts/debts/snapshots/audit plus snapshotAccounts, all integers; receipt verification is required before the frontend marks a legacy migration complete.

## Frontend boundary

The current [AuthScreen](./src/auth/AuthScreen.tsx) offers login only and calls `auth.login`; it does not read `VITE_PUBLIC_REGISTRATION` or expose a registration mode, including in development. The production build still supplies that public flag, but the UI does not depend on it. Access is provided by the owner. HTTP registration remains available outside production; the production controller gate described above is independent of the frontend.

`useLedger` exposes LedgerContextValue; `useAuth` exposes separate auth state and stable functions. `exportServerBackup():Promise<Result<string>>` calls the actual server export endpoint. Settings uses this async fresh export, not the cached synchronous serializer. There is no offline write fallback. Cache clears immediately on user change/logout/401 and generation checks reject late responses from prior sessions. Every protected request carries its captured expected user ID, including import receipt proof; a binding rejection expires stale frontend auth and clears its ledger cache. Logout captures the user before local invalidation and binds revocation to that identity; if a login is pending, it waits and uses the identity returned by that login without publishing a cancelled login. Legacy IndexedDB is read-only: no automatic creation, upgrade, deletion or upload. After login, migration requires preview of source and destination plus explicit confirmation; server receipt is verified before completion.

## Local operations

Local stack uses database port 5439. The API runtime DATABASE_URL uses a non-superuser application role. Administrative credentials are passed only to migration/bootstrap CLI processes. [with-local-db.mjs](./scripts/with-local-db.mjs) injects environment without writing credential files or printing URLs.

## Automatic monthly account closes

MonthlyCloseModule registers one named cron `monthly-account-close`, expression `0 0 0 1 * *`, IANA timezone `Europe/Kyiv`, waitForCompletion enabled. The same catchup runs on application bootstrap; there is no periodic server poll. Failures (including workspace-list outages) get only three one-off retries after 30 seconds, 2 minutes and 10 minutes; success ends the chain, shutdown cancels the timer, and overlapping passes coalesce. Exhaustion is logged and the next opportunity is startup or the next monthly cron. Each active workspace is locked and processed independently so one damaged workspace does not block others. A run inserts all eligible missing month boundaries and advances the workspace revision once if it inserted any; Snapshot `(datasetId,closedMonth)` uniqueness provides idempotency across instances/restarts. No public scheduler trigger or test endpoint exists.

AccountHistory stores datasetId/accountId/revision/effectiveAt/name/owner/provider/balanceMinor/position, with composite primary key `(datasetId,accountId,revision)`, money/revision/provider constraints and lookup index. Dataset.accountHistoryStartedAt starts null on migration and is initialized from the full current account state under its workspace lock. Each account.create/update/setBalance appends a full version. New workspaces establish their own actual-time anchor; imports use the same single post-lock serialized transition timestamp for closing/archiving the old dataset, the new dataset anchor and import receipt, even if physical row insertion crosses midnight; legacy BalanceChange/import_opening rows and snapshots remain intact. PostgreSQL `date_trunc('milliseconds',clock_timestamp())` is obtained after lock acquisition, not transaction-start `now()`. This is serialized event time; a transaction may physically commit later. At boundary B, only versions with effectiveAt < B participate, ordered by effectiveAt and then revision. No eligible pre-anchor boundary is fabricated.

Snapshot.closedMonth is optional on the wire and nullable in SQL. Explicit `YYYY-MM` markers require an exact createdAt equal to the next Kyiv month boundary and unique closedMonth in a document. Old documents remain valid with the key absent; manual snapshots are retained but never inferred to be official from dates, labels or IDs. Explicit valid markers survive backup import/export; their restoration does not backdate journal coverage. New HTTP `snapshot.create` commands return 400 VALIDATION; the old pure domain variant remains for legacy data and audit compatibility.

Import closes eligible missed months of the old active dataset before archive/activation in the same locked transaction. Internal AccountHistory is not part of DocumentV1; restoring JSON creates a new actual-time anchor while retaining supplied official and manual snapshots. Monthly UI differences use only the previous official closedMonth; safe stored totals can yield an out-of-range derived difference, reported explicitly rather than invalidating the ledger.
